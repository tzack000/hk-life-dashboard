## Context

`/property` 现有「租房」「购房」两种视图，数据来自 `scraper/scrape_centanet.py`：每日写入 SQLite `rental.db`，导出 `transactions.json`，前端 `useRentalData` 读取，失败则用 `src/data/mock-transactions.ts`。页面在 `App.tsx` 里保持挂载，筛选状态因此不会因路由切换丢失。成交关注区域固定为启德、荃湾西、大埔墟、将军澳。

一手新盘和二手成交不是同一份列表，地理范围也不相同。新盘以启德站为中心，只看地铁大约 30 分钟能到的项目。新盘要保留状态、售价和关键日期的变化，不能每次采集只覆盖一份快照。

## Goals / Non-Goals

**Goals:**

- 在现有房产看板上增加「新盘」视图，范围是启德站 30 分钟地铁圈。
- 每日采集这个圈内的一手住宅项目，标出最近车站和大约分钟数，并记录可见变化。
- 沿用「JSON 文件 + 前端降级」的数据路径，不新增对外 API。

**Non-Goals:**

- 不覆盖全港新盘，也不把成交页的四个区域原样套到新盘上。
- 通勤方式只算地铁。不把出站后步行、巴士、小巴、轻铁、驾车或渡轮算进 30 分钟。
- 不采集价单 PDF、销售安排全文或成交登记册。
- 不改租房、购房的统计、图表和成交表。
- 不把新盘做成独立路由。

## Decisions

### 视图放在现有页头，而不是新页面

`Header` 的租房/购房切换扩成三项：「租房」「购房」「新盘」。`txType` 增加 `'launch'`。选中「新盘」时页头显示「启德地铁 30 分钟内」，只保留销售状态筛选。成交用的区域、月份、小区、房型不渲染，避免把四个成交区域误解成新盘范围。

成交筛选仍留在现有 hook 里。销售状态（全部 / 即将推售 / 发售中 / 已售罄）放在新的 `useNewLaunches` 中。`/property` 区块保持挂载，两套状态都不会因切走页面或切换视图被重置。

新盘列表用独立区块替换成交统计、图表和成交表，不把新盘行混进 `TransactionTable`。

### 单独脚本采集，写入同一数据库的新表

新增 `scraper/scrape_new_launches.py`，不并进 `scrape_centanet.py`。成交爬虫失败不应挡住新盘，反过来也一样。cron 在现有成交任务之后调用新脚本。

数据来源用中原地产的新盘列表，与现有成交同源，页面来源文案继续写「中原地产」。实现时对照当时的新盘列表页确认请求地址和字段；若页面是 NUXT，沿用现有「取页面数据再解析」的方式，不靠会被压缩变量名破坏的正则。

通勤圈用一份固定车站清单，放在 `scraper/kai-tak-mtr-30.json`，和脚本一起部署。不抓取港铁行程规划器。分钟数是站台到站台的大约值：屯马线站间用公开行车时间的上限，其他重铁站间按 2 分钟、跨海或长区间按 3 到 4 分钟；起点候车计 3 分钟一次；每次换乘加 5 分钟；尖东走到尖沙咀计 4 分钟。结果取整数，超过 30 的站不收入。

圈内包括启德、宋皇台、土瓜湾、何文田、红磡、尖东、尖沙咀、柯士甸、南昌、美孚、荃湾西、钻石山、显径、大围至马鞍山（不含乌溪沙）、沙田、火炭、大学、黄大仙至调景岭（不含将军澳各站）、九龙塘、石硖尾、太子、旺角、油麻地、黄埔、深水埗、长沙湾、奥运、荔景、会展、金钟、中环、湾仔。紧邻但排除的边界站是锦上路、乌溪沙、大埔墟、将军澳、铜锣湾、上环、荔枝角、九龙站。轻铁、机场快线和港岛南线不收入。

项目用地点、屋苑名对照清单里的车站别名。能对上多个站时取分钟数最少的一个。对不上的名称记入日志并丢弃，不猜测。

表：

- `new_launches`：稳定 id、名称、最近车站、到启德分钟数、发展商、地址、状态、下一关键日期、单位数目、最低售价、尺价、来源链接、最后见到时间
- `launch_events`：项目 id、日期、类型（`appeared` / `status` / `price` / `date`）、摘要

每次采集按 id 更新项目。和上一行相比，状态、最低售价或下一关键日期有变化才追加一条动态；第一次见到记为 `appeared`。已有动态不删除。连续多次未出现的项目保留最后状态，不从库里抹掉，这样「已售罄」和历史动态还在。

导出 `data/new-launches.json`，不改 `transactions.json`：

```json
{
  "lastUpdated": "2026-10-08T02:10:00+08:00",
  "source": "中原地产",
  "launches": [],
  "events": []
}
```

`events` 只带每个项目最近若干条，供页面展开，避免文件无限变大。数据库里仍保留全量。

### 前端读取与排序

`useNewLaunches` 请求 `./data/new-launches.json`。有至少一条新盘则用服务器数据；失败或空列表则用 `src/data/mock-new-launches.ts`，并分开标记来源。这个请求和 `transactions.json` 互不影响。

导出的每条新盘带 `nearestStation` 和 `minutesToKaiTak`。前端丢掉分钟数大于 30 或车站不在清单中的行，避免旧文件把圈外项目显示出来。排序：发售中、即将推售、已售罄，同状态内按通勤分钟从少到多，分钟数相同再按下一关键日期由近到远。售价缺失时显示「售价待公布」。条目写「宋皇台站 · 约 5 分钟」。最新动态取该项目日期最新的一条；展开区按日期倒序。

首页卡片说明改为「各区域租赁与购房成交，以及启德 30 分钟地铁圈的新盘」。

### 部署

爬虫：`scp` 到服务器后 `sudo cp` 到 `$SCRAPER_DIR`，手动跑一次确认导出文件。前端构建后 `rsync` 必须带目录执行权限，并 `--exclude data`，避免删掉服务器上的 `new-launches.json` 和 `transactions.json`。本地没有这份 JSON 时，开发服务器会显示示例数据，这不代表线上数据丢失。

## Risks / Trade-offs

- [中原新盘页结构变化导致采集为空] → 脚本失败时不覆盖已有 JSON；日志写明解析结果为零。页面继续显示上次成功的文件。
- [车站别名漏掉新楼盘所在的小地名] → 未对照的名称打日志，不猜测最近车站，避免把圈外项目显示进看板。
- [分钟数是估算，不是行程规划器的实时结果] → 清单写死并可审阅；边界站明确排除。以后若要改口径，只改这份清单。
- [售价在价单公布前经常为空] → 空价是正常状态，用「售价待公布」，不用 0。
- [动态只比较采集到的字段] → 价单份数、折扣、余货不在本次字段内，这些变化不会产生动态。

## Migration Plan

1. 先部署并手动执行新脚本，确认 `new-launches.json` 生成且 `transactions.json` 未被改写。
2. 再部署前端。前端先上线也安全：文件不存在时走示例数据。
3. 回滚时去掉 cron 中的新脚本，并部署不含「新盘」视图的前端。JSON 和数据表可留着，不参与成交页。
