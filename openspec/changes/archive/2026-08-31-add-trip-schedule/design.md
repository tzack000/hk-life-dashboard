# 设计：新增「近期行程」视图

> 本变更以「补规范 + 修正漂移」为主，功能代码已存在，此处记录关键设计决策与取舍。

## 1. 数据来源：静态模块而非 API

家庭日程走 `analytics_server.py` 同款 Flask + SQLite + systemd 架构，行程**不沿用**这套。

理由：
- 行程是单次、低频、高度定制的内容（逐日安排、预订编号、注意事项），用数据库建模收益低
- 行程信息整理自个人笔记，以 TS 模块形式与代码同仓管理，改动可走 PR review
- 家庭日程面向长期、持续增删的日常事件，行程面向一次性出行，两者的更新频率与维护者不同

代价：修改行程需要改代码 + 重新部署，不能像日程那样用自然语言交给 AI Agent 维护。若后续行程数量增多再考虑引入后端。

数据位置：`src/data/trips/okinawa-2026.ts`，导出 `trips: Trip[]` 与 `snorkelNotes: string[]`；新增行程即新增同构模块并在 `useTrips` 中聚合。

## 2. 行程状态派生

`buildTripState()` 以「今天零点」为基准计算，避免时分秒干扰天数差：

| 字段 | 含义 |
|------|------|
| `phase` | `upcoming`（未开始）/ `ongoing`（进行中，含首尾日）/ `past`（已结束） |
| `daysToStart` | 距出发天数，进行中为 0 |
| `daysRemaining` | 进行中剩余天数（含今天），其余为 0 |
| `currentDay` | 进行中时命中的 `TripDay`，用于高亮「今天」 |
| `progress` | 未开始 0 / 已结束 100 / 进行中按已过天数占比 |

选择规则：`useTrips` 默认选中进行中的行程，其次未开始的最近一场；`useUpcomingTrip(30)` 供家庭日程取「近期需要关注的行程」，同样是进行中优先。

## 3. 视图切换与默认视图

三个视图在 `App.tsx` 中**始终挂载**，用 `hidden` class 切换显隐，因此切换视图不会重置各自的筛选状态（与家庭日程变更 6.2 的做法一致）。

默认视图按 `family-schedule` 规范的「默认首页」定义为 `family`。导航顺序为 近期行程 / 家庭日程 / 房产看板 —— 「近期行程」占位首位（出行场景下最高频），但不改变默认落点。

## 4. 与家庭日程的耦合

家庭日程「近期事件」区块顶部会渲染 `TripBanner`（即将到来 / 进行中的行程摘要）。这是**唯一**的跨能力耦合，且方向是单向的：行程模块不依赖家庭日程，家庭日程只读取 `useUpcomingTrip()`。

`TripBanner` 在 `upcomingTrip` 为 `null` 时不渲染，因此无近期行程时家庭日程行为完全不变。

## 5. 展示结构

- 概览卡：标题、倒计时徽章、目的地、日期区间、天数/晚数/人数、一句话概览、进度条、事件类型统计
- 逐日区块（左，占 2 列）：`Day N` 徽章、日期周几、当日标题、事件卡片列表、当天待办、待补信息（待补用玫红警示块）
- 侧栏（右，占 1 列）：预订状态、出发前任务（P0/P1/P2 分组）、浮潜注意事项
- 事件卡片：类型徽章 + 预订状态徽章 + 时间/地点/费用/地图外链/备注，重要事件用琥珀底高亮

筛选：按事件类型（全部 / 交通 / 住宿 / 活动 / 餐饮 / 其它）过滤，同时作用于所有日区块；筛选后空日程显示占位文案而非隐藏区块。

## 6. 风险与验证

- 默认视图改动会影响已上线行为：需 `npm run build` 通过后部署前端（`--exclude data`）
- 日期计算依赖本地时区，跨时区查看可能有一天偏差；当前用户场景固定在香港时区，暂不处理
- 行程为静态数据，无降级需求，不存在 API 失败路径
